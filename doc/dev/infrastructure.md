# Инфраструктура репозитория и окружение разработки

Данный документ описывает структуру репозитория проекта **«Вишенка» (Wishenka)**, систему автоматизации жизненного цикла разработки (Makefile), стандарты кодовой базы, тестирование, управление конфигурацией, контейнеризацию и пайплайн непрерывной интеграции (CI).

---

## 1. Обзор структуры репозитория

Проект организован по модульному принципу в соответствии с современными стандартами разработки на Python (Packaging per PEP 517/621 с бэкендом `hatchling`):

```text
wishenka/
├── .github/
│   └── workflows/
│       └── ci.yml             # GitHub Actions Quality Gate pipeline
├── ai-tasks/                  # Артефакты задач Top-Down workflow
├── doc/
│   └── dev/                   # Документация для разработчиков
│       ├── architecture.md    # Высокоуровневая архитектура сервиса
│       ├── infrastructure.md  # Инфраструктура, Makefile, линтеры и CI
│       └── testing.md         # Browser UI-тесты и подготовка Chromium
├── in-docs/                   # Функциональные спецификации продукта
├── specs/                     # Высокоуровневые концепции и роли
├── tests/                     # Автоматизированные тесты (Pytest)
│   ├── test_infra.py          # Тесты инфраструктуры и базового приложения
│   └── test_observability.py  # Тесты структурированного логирования
├── wishenka/                  # Исходный код пакета приложения
│   ├── __init__.py            # Версия пакета (__version__)
│   ├── config.py              # Конфигурация приложения (Pydantic Settings)
│   ├── logging.py             # Настройка структурированного логирования (JSON/text)
│   ├── main.py                # Точка входа для запуска ASGI-сервера (uvicorn)
│   └── web/                   # Веб-слой (FastAPI, HTMX, эндпоинты)
│       ├── __init__.py
│       └── app.py             # Фабрика приложения create_app() и middleware
├── docker-compose.yml         # Локальный запуск сервиса в контейнере
├── Dockerfile                 # Многоэтапный Docker-образ (multi-stage)
├── Makefile                   # Автоматизация типовых сценариев разработки
├── pyproject.toml             # Зависимости, метаданные и настройки инструментов
└── README.md                  # Краткое руководство по быстрому старту
```

## 2. Команды Makefile и жизненный цикл разработки

Для унификации операций локальной разработки, проверки качества кода и запуска в CI используется `Makefile`. Все команды выполняются в локальном виртуальном окружении `.venv`.

### 2.1. Доступные команды

| Команда | Описание |
| --- | --- |
| `make help` | Отображает интерактивный список всех доступных команд с кратким описанием (действие по умолчанию). |
| `make venv` | Создает виртуальное окружение `.venv` (если отсутствует) и обновляет `pip`. |
| `make deps` | Создает `.venv` и устанавливает проект в editable-режиме вместе с dev-зависимостями (`pip install -e ".[dev]"`). |
| `make deps-browser` | Готовит Chromium/Chrome для browser UI-тестов: находит и проверяет браузер, на Debian без браузера ставит `chromium` через `apt-get`. Не входит в `make test` и `make check`; подробности в [testing.md](testing.md). |
| `make build` | Проверяет синтаксическую корректность и компилируемость Python-файлов через `python -m compileall`. |
| `make analyze` | Запускает полный статический анализ: линтер `ruff check`, проверку стиля `ruff format --check` и статический анализатор типов `mypy`. |
| `make format` | Автоматически форматирует код (`ruff format`) и применяет безопасные автофиксы (`ruff check --fix`). |
| `make test` | Запускает набор автоматизированных тестов с помощью `pytest`. |
| `make check` | **Единый Quality Gate**: последовательно выполняет `make analyze` и `make test`. Обязателен перед созданием коммита. |
| `make run` | Запускает локальный сервер разработки `uvicorn wishenka.main:app` с флагом `--reload` на порту 8000. |
| `make clean` | Очищает артефакты сборки, кэши инструментов (`.pytest_cache`, `.ruff_cache`, `.mypy_cache`) и байткод `__pycache__`. |

### 2.2. Типовой рабочий процесс разработчика

```bash
# 1. Первичная настройка окружения
make deps

# 2. Локальный запуск сервера разработки
make run

# 3. Автоматическое форматирование кода после внесения изменений
make format

# 4. Прохождение единого шлюза качества перед коммитом
make check
```

## 3. Стандарты кода и статический анализ

В проекте установлены строгие требования к качеству кода, стилю и статической типизации. Конфигурация зафиксирована в `pyproject.toml`.

### 3.1. Линтер и форматтер (Ruff)

- **Версия Python:** 3.12 (`target-version = "py312"`).
- **Максимальная длина строки:** 100 символов (`line-length = 100`).
- **Активированные наборы правил:**
  - `E` / `W`: ошибки и предупреждения стиля PEP 8 (pycodestyle).
  - `F`: поиск синтаксических ошибок, неиспользуемых переменных и импортов (pyflakes).
  - `I`: автоматическая сортировка и группировка импортов (isort). Модуль `wishenka` помечен как `known-first-party`.
  - `B`: предотвращение типичных ошибок и багов (flake8-bugbear).
  - `C4`: оптимизация синтаксиса списковых и словарных включений (flake8-comprehensions).
  - `UP`: автоматическая модернизация синтаксиса до Python 3.12+ (pyupgrade).
  - `SIM`: упрощение логических выражений и конструкций (flake8-simplify).

### 3.2. Статическая типизация (Mypy)

- **Строгий режим:** включен глобально (`strict = true`).
- Все функции и методы основного пакета `wishenka` обязаны содержать полные аннотации типов аргументов и возвращаемых значений (`disallow_untyped_defs = true`, `disallow_incomplete_defs = true`).
- Неявные `Optional` запрещены (`no_implicit_optional = true`).
- Включен плагин `pydantic.mypy` для корректной валидации моделей конфигурации и DTO.
- Для директории `tests/` ослаблено требование явных аннотаций сигнатур тестов, при этом проверка тел функций сохраняется (`check_untyped_defs = true`).

## 4. Требования и правила тестирования

Автоматизированные тесты располагаются в директории `tests/` и выполняются через фреймворк `pytest`.

### 4.1. Контракт таймаута тестов (10-секундный лимит)

Для исключения зависания тестов при выполнении асинхронных операций, взаимодействии с сетью или блокировках базы данных действует обязательный контракт:
- Каждый тестовый модуль **обязан** содержать глобальную директиву таймаута:
  ```python
  import pytest

  pytestmark = pytest.mark.timeout(10)
  ```
- Если тесту требуется больше времени (например, комплексный интеграционный сценарий), допустимо переопределение на уровне конкретной функции: `@pytest.mark.timeout(30)`.

### 4.2. Асинхронные тесты

- Используется библиотека `pytest-asyncio`.
- Режим выполнения настроен в `pyproject.toml`:
  ```toml
  [tool.pytest.ini_options]
  asyncio_mode = "auto"
  asyncio_default_fixture_loop_scope = "function"
  ```
- Это позволяет объявлять тестовые функции напрямую как `async def test_something():` без дополнительных декораторов.

### 4.3. Тестирование веб-эндпоинтов и логирования

- Для тестирования FastAPI-эндпоинтов используется `fastapi.testclient.TestClient`.
- Для проверки записей структурированного журнала применяется стандартная фикстура `caplog`:
  ```python
  def test_logging(caplog: pytest.LogCaptureFixture) -> None:
      with caplog.at_level(logging.INFO):
          ...
  ```

## 5. Управление конфигурацией приложения

Конфигурация сервиса реализована в `wishenka/config.py` с помощью библиотеки `pydantic-settings`.

### 5.1. Загрузка параметров

Параметры считываются из следующих источников (в порядке приоритета):
1. Переменные окружения с префиксом `WISHENKA_` (например, `WISHENKA_DATABASE_URL`).
2. Файл `.env` в корневой директории проекта (если присутствует).
3. Значения по умолчанию, заданные в классе `Settings`.

### 5.2. Таблица параметров конфигурации

| Переменная окружения | Поле `Settings` | Тип | По умолчанию | Описание |
| --- | --- | --- | --- | --- |
| `WISHENKA_APP_NAME` | `app_name` | `str` | `"wishenka"` | Имя приложения в метаданных и логах. |
| `WISHENKA_ENVIRONMENT` | `environment` | `str` | `"development"` | Окружение запуска (`development`, `production`, `test`). |
| `WISHENKA_DEBUG` | `debug` | `bool` | `False` | Флаг отладочного режима. |
| `WISHENKA_LOG_LEVEL` | `log_level` | `str` | `"INFO"` | Уровень логирования (`DEBUG`, `INFO`, `WARNING`, `ERROR`). |
| `WISHENKA_LOG_JSON` | `log_json` | `bool` | `False` | Формат логов: `True` для structured JSON, `False` для plain text. |
| `WISHENKA_SQLITE_DB_PATH` | `sqlite_db_path` | `str` | `"data/wishenka.db"` | Путь к файлу базы данных SQLite. |
| `WISHENKA_DATABASE_URL` | `database_url` | `str` | `"sqlite+aiosqlite:///data/wishenka.db"` | URL подключения SQLAlchemy/aiosqlite. |
| `WISHENKA_BOT_TOKEN` | `bot_token` | `str` | `""` | Секретный токен Telegram Bot API. |

## 6. Контейнеризация и Docker Compose

Для деплоя и локального запуска в изолированной среде подготовлены `Dockerfile` и `docker-compose.yml`.

### 6.1. Многоэтапная сборка (Dockerfile)

Dockerfile использует два этапа (multi-stage build) на базе образа `python:3.12-slim`:
1. **Этап `builder`**:
   - Устанавливает минимальные системные зависимости компиляции (`build-essential`).
   - Создает виртуальное окружение `/opt/venv` и выполняет установку проекта `pip install .`.
2. **Этап `runtime`**:
   - Создает выделенного непривилегированного пользователя `appuser` с UID/GID `10001` (соответствие рекомендациям безопасности CIS Docker).
   - Копирует готовое окружение `/opt/venv` из этапа сборки (минимизируя итоговый размер образа).
   - Создает директорию `/app/data` для хранения базы данных SQLite и назначает права `appuser:appgroup`.
   - Настраивает периодический `HEALTHCHECK` с проверкой эндпоинта `/healthz`.
   - Запускает сервис под пользователем `appuser` через `uvicorn`.

### 6.2. Docker Compose

Файл `docker-compose.yml` настраивает локальный запуск контейнера:
- Проброс порта `8000:8000`.
- Монтирование именованного тома `sqlite_data` в директорию `/app/data` для сохранения состояния базы данных SQLite между перезапусками.
- Монтирование исходного кода `./wishenka` в режиме read-only (`:ro`) для удобной локальной разработки.

Запуск контейнера:
```bash
docker compose up --build
```

Проверка работоспособности:
```bash
curl http://localhost:8000/healthz
# Ответ: {"status":"ok"}
```

## 7. Пайплайн непрерывной интеграции (GitHub Actions CI)

Конфигурация пайплайна находится в `.github/workflows/ci.yml`.

### 7.1. Условия запуска

Воркфлоу запускается автоматически при:
- Создании `push` в ветки `main` и `master`.
- Создании или обновлении `pull_request` в ветки `main` и `master`.

### 7.2. Шаги выполнения

1. **Checkout repository**: клонирование репозитория через `actions/checkout@v4`.
2. **Set up Python 3.12**: развертывание среды Python 3.12 с кэшированием pip-зависимостей (`actions/setup-python@v5`).
3. **Install dependencies**: вызов `make deps` для установки проекта и dev-пакетов.
4. **Install browser for UI tests**: вызов `make deps-browser`: проверяет браузер, предустановленный в образе `ubuntu-latest`; если подходящего нет, шаг падает с понятным сообщением (см. [testing.md](testing.md)).
5. **Run Quality Gate**: вызов `make check`, который последовательно проверяет форматирование, линтер, строгую типизацию Mypy и запускает тесты Pytest.

Browser UI-тесты в CI не пропускаются: при отсутствии браузера они завершаются ошибкой, а `WISHENKA_SKIP_BROWSER_TESTS=1` в CI игнорируется.

Любое предупреждение линтера, ошибка типов или упавший тест немедленно блокируют сборку.

## 8. Устранение типичных неполадок (Troubleshooting)

### 8.1. Ошибки линтера или форматирования при `make check`

**Симптом:** `make check` завершается с ошибкой на этапе `ruff format --check` или `ruff check`.  
**Решение:** Выполните команду автоматического форматирования:
```bash
make format
```
Большинство проблем с отступами, сортировкой импортов и устаревшим синтаксисом исправляются автоматически.

### 8.2. Ошибки типизации Mypy (`Missing return statement`, `Function is missing a type annotation`)

**Симптом:** `make analyze` выдает ошибку о пропущенных типах в сигнатуре функции.  
**Решение:** В репозитории включен `strict = true`. Каждая функция в `wishenka/` должна явно декларировать типы аргументов и возвращаемого значения (включая `-> None` для функций без возврата):
```python
def my_function(param: str) -> None: ...
```

### 8.3. Падение тестов по таймауту (`Failed: Timeout >10.0s`)

**Симптом:** Тест завершается ошибкой `Failed: Timeout >10.0s` от `pytest-timeout`.  
**Решение:** 
- Убедитесь, что асинхронный вызов не ожидает внешних сетевых ресурсов без моков.
- При обращении к SQLite убедитесь, что транзакции закрываются и соединение не заблокировано другим потоком.
- Если тесту объективно требуется больше времени, переопределите таймаут для отдельного теста: `@pytest.mark.timeout(30)`.

### 8.4. Ошибка прав доступа к базе данных SQLite в Docker (`sqlite3.OperationalError: unable to open database file`)

**Симптом:** При запуске в Docker сервис падает при попытке создать или открыть `data/wishenka.db`.  
**Решение:** Контейнер запускается под непривилегированным пользователем `appuser` (UID 10001). Убедитесь, что директория `/app/data` смонтирована как volume `sqlite_data` (где права автоматически выставляются сервисом) или локальный каталог имеет права на запись для UID 10001.

### 8.5. Нет Chromium для browser UI-тестов (`Chromium is required for browser UI tests`, snap-заглушка)

**Симптом:** браузерные тесты завершаются ERROR at setup, а `make deps-browser` выходит с кодом `2` (браузер не найден) или `3` (найден, но не запускается, например snap-заглушка `/usr/bin/chromium`).  
**Решение:** выполните `make deps-browser` (на Debian пакет ставится автоматически). На Ubuntu и других системах установите Chromium из Debian или Google Chrome и задайте путь: `export WISHENKA_CHROMIUM_BIN=/path/to/chrome`. Snap Chromium не поддерживается. Локальный пропуск: `WISHENKA_SKIP_BROWSER_TESTS=1` (в CI не действует). Подробности: [testing.md](testing.md).

### 8.6. Пересоздание окружения «с нуля»

**Симптом:** Несогласованные зависимости или поврежденный `.venv`.  
**Решение:**
```bash
make clean
rm -rf .venv
make deps
make check
```
