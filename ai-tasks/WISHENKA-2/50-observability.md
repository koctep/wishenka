# WISHENKA-2: Observability Implementation

## Overview

Задача WISHENKA-2 посвящена фиксации архитектурных договоренностей, выбору стека и проектированию схемы БД. В рамках задачи не создается исполняемый runtime-код, однако в документе архитектуры (`20-architecture.md`) спроектирована целостная стратегия наблюдаемости для последующих задач реализации.

## Architectural Observability Strategy

### 1. Structured Logging
- Использование стандартного syslog/Python `logging` (или `structlog`) с выводом в формате JSON для легкого парсинга в production.
- Разделение уровней логирования:
  - `INFO`: запуск приложения, авторизация пользователя через Telegram initData, создание вишлиста, успешное бронирование, отметка о получении подарка.
  - `WARNING`: повторные попытки отправки через Telegram Bot API (rate limit / 429 Retry-After), fallback парсера ссылок на ручной ввод при таймауте внешнего сайта.
  - `ERROR`: сбои аутентификации initData (неверный HMAC), ошибки целостности базы данных SQLite, ошибки отправки уведомлений после исчерпания попыток.
- **Инвариант сюрприза в логах**:
  - Строгий запрет на логирование персональных данных дарителя рядом с идентификатором вишлиста в открытом виде там, где логи могут просматриваться получателем.
  - В логах бронирования не выводятся детали подарка в контексте сессии владельца вишлиста.

### 2. Transactional Outbox Monitoring
- Воркер отправки сообщений отслеживает состояние таблицы `notification_outbox`:
  - Количество сообщений в очереди (`status = 'pending'`).
  - Ошибки доставки (`status = 'failed'`, `retry_count >= 3`).
  - Лаг доставки (разница между `created_at` и `sent_at`).

### 3. Healthcheck & Metrics
- Эндпоинт `/healthz` для проверки готовности сервиса (проверка доступности файла SQLite БД, статус фонового воркера бота).
