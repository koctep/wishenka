# WISHENKA-132: Освобождать ресурсы WishlistStore при ошибке initialize()

## Goals

Обеспечить надёжное и предсказуемое освобождение системных ресурсов (соединений с базой данных и временных файлов) при неуспешной инициализации хранилища списков желаний (`WishlistStore`).

Бизнес-ценность:
- Исключение утечек файловых дескрипторов, временных файлов на диске и пулов соединений в сценариях запуска сервисов, административных скриптов и автоматических тестов при ошибках старта или миграции хранилища.
- Снижение риска исчерпания дискового пространства и ресурсов ОС в средах разработки, тестирования и эксплуатации при повторных неудачных запусках.
- Снижение нагрузки на вызывающий код: скрипты и тесты не обязаны помнить о ручной очистке ресурсов, если инициализация завершилась ошибкой.

## User Stories

- **Как разработчик или оператор, запускающий скрипт или сервис**, я хочу, чтобы при ошибке инициализации `WishlistStore` все выделенные для него ресурсы автоматически освобождались, чтобы на диске не оставались бесхозные временные файлы и не висели открытые подключения к базе данных.
- **Как автор тестов**, я хочу вызывать инициализацию in-memory хранилища напрямую без обязательной обёртки для очистки при сбое, чтобы падение инициализации не приводило к утечке временных файлов в системе.
- **Как владелец жизненного цикла веб-приложения**, я хочу, чтобы повторное освобождение ресурсов хранилища на этапе завершения работы приложения оставалось безопасным и не приводило к ошибкам, даже если ресурсы уже были освобождены при сбое инициализации.

## Definition of Done

1. Язык реализации зафиксирован: **Python**.
2. При любом неуспешном завершении инициализации `WishlistStore`:
   - Все ресурсы, выделенные экземпляру хранилища (соединения с базой данных и принадлежащий ему временный файл при работе в режиме `:memory:`, включая сопутствующие служебные файлы, если они создавались), полностью освобождаются до возврата управления вызывающему коду.
   - Ошибка инициализации по-прежнему передаётся вызывающему коду в соответствии с контрактом (исключение не подавляется).
3. Поведение для файловых баз данных (не `:memory:`):
   - При ошибке инициализации освобождаются соединения с базой данных, при этом сама пользовательская/постоянная база данных на диске не удаляется.
4. Идемпотентность освобождения ресурсов:
   - Если вызывающий код (например, обработчик жизненного цикла веб-приложения) дополнительно вызывает освобождение ресурсов после неуспешной инициализации, повторная операция завершается корректно и без ошибок.
5. Автоматические тесты подтверждают:
   - При сбое инициализации `:memory:`-хранилища временный файл отсутствует на диске после завершения вызова, а ресурсы подключений освобождены.
   - При сбое инициализации файлового хранилища сам файл базы данных сохраняется, а ресурсы подключений освобождены.
   - Повторный вызов освобождения ресурсов после неудачной инициализации безопасен и не вызывает исключений.
   - Существующий набор тестов проекта продолжает проходить без регрессий.

## Task Description

### Контекст проблемы

При создании экземпляра `WishlistStore` для хранилища в памяти (`:memory:`) система выделяет временный файл на диске и инициализирует движок подключений к базе данных. Последующий шаг инициализации (`initialize()`) подготавливает схему базы данных.

Если на этапе инициализации происходит сбой:
- Жизненный цикл основного веб-приложения защищён, так как гарантированно вызывает освобождение ресурсов при завершении.
- Однако скрипты, CLI-утилиты и тесты, вызывающие инициализацию напрямую, при возникновении ошибки не получают автоматического освобождения ресурсов: в результате на диске утекает временный файл (для `:memory:`), а движок подключений остаётся неосвобождённым.

### Область применения (Scope)

- **Входит в задачу**:
  - Гарантия освобождения ресурсов экземпляра `WishlistStore` при неуспешном завершении `initialize()`.
  - Совместимость с последующим явным вызовом `dispose()` вызывающим кодом (включая сценарий завершения работы веб-приложения).
  - Тестовое покрытие сценариев ошибки инициализации для `:memory:` и файлового хранилища, а также повторного освобождения ресурсов.
- **Не входит в задачу**:
  - Изменение формата сообщений об ошибках инициализации или пересмотр политики обработки исключений (покрывается отдельными задачами при необходимости).
  - Рефакторинг способов создания `:memory:`-хранилища.
  - Изменение мест вызова `dispose()` в сторонних тестах (отдельная задача `WISHENKA-134`).

### Функциональные требования

1. При успешном выполнении `initialize()` поведение системы не изменяется: хранилище готово к работе, ресурсы остаются активными до явного вызова `dispose()`.
2. При возникновении ошибки во время `initialize()` хранилище должно освободить свои ресурсы до проброса исключения вызывающему коду.
3. Оригинальный контракт ошибок при сбое `initialize()` должен сохраняться (вызывающий код получает ожидаемое исключение инициализации).
4. После сбоя `initialize()` последующий вызов `dispose()` на том же экземпляре не должен приводить к ошибке.

### Нефункциональные требования

- **Надёжность**: освобождение ресурсов должно происходить при любом типе ошибки инициализации, не оставляя «висячих» временных файлов `:memory:`-хранилища.
- **Безопасность данных**: постоянные файлы баз данных (не `:memory:`) ни при каких обстоятельствах не должны удаляться при ошибке инициализации.
- **Совместимость**: существующие сценарии жизненного цикла веб-приложения и бота должны продолжать работать без изменений со стороны вызывающего кода.

### Ограничения и допущения

- Предполагается, что после неуспешной инициализации экземпляр `WishlistStore` не используется для чтения или записи данных; допустим только повторный вызов `dispose()` в блоках очистки вызывающего кода.
- Язык реализации: **Python** (согласно существующей кодовой базе проекта).

### Основные сущности (доменный уровень)

- **Хранилище списков желаний (`WishlistStore`)**: компонент, управляющий доступом к данным списков желаний и владеющий ресурсами подключения к базе данных и (в режиме `:memory:`) временным файлом хранилища.
- **Инициализация хранилища (`initialize`)**: операция подготовки хранилища и приведения схемы данных к актуальному состоянию перед началом работы.
- **Освобождение ресурсов (`dispose`)**: операция закрытия подключений и удаления временных файлов, принадлежащих экземпляру хранилища.
- **Вызывающий код (Lifespan / Скрипт / Тест)**: внешний потребитель, создающий и инициализирующий хранилище; может как вызывать `dispose()` в собственном обработчике завершения, так и не делать этого при ошибке.

## Q&A

- **В:** Нужно ли изменять обработчик жизненного цикла веб-приложения (`lifespan`), где уже вызывается `dispose()`?
  **О:** Нет, `lifespan` уже защищён; достаточно, чтобы повторный вызов `dispose()` после неуспешной инициализации оставался безопасным.
- **В:** Что должно происходить с файлом базы данных, если хранилище настроено на постоянный файл, а не на `:memory:`?
  **О:** Постоянный файл базы данных принадлежит пользователю/системе и не должен удаляться; освобождаются только соединения с базой данных.
