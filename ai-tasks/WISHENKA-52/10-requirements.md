# WISHENKA-52: [Техдолг] Неблокирующий разбор HTML тяжёлых страниц

## Goals

Сервис «Вишенка» обслуживает много пользователей одним процессом. Когда пользователь вставляет ссылку на товар, сервис загружает страницу магазина и извлекает из неё название, фото, цену и магазин. Страницы маркетплейсов бывают тяжёлыми (больше 1 МБ). Разбор такой страницы сейчас занимает заметное время, и пока он идёт, сервис не обрабатывает запросы остальных пользователей: веб-интерфейс и Telegram-бот «замирают».

Бизнес-цель: один пользователь, вставивший ссылку на тяжёлую страницу, не должен ухудшать отзывчивость сервиса для остальных. Результат извлечения метаданных при этом не должен меняться.

Почему это нужно (ответ на «Why?»): задача сформулирована как техдолг. Базовая потребность — сохранить быстрый отклик («эмоционально лёгкий» продукт) при росте числа пользователей и размера страниц. Способ решения (отдельный поток или быстрый парсер) относится к архитектуре и выбирается на Шаге 2.

## User Stories

- Как **владелец вишлиста**, я вставляю ссылку на тяжёлую страницу магазина и получаю предпросмотр товара, как и раньше.
- Как **другой пользователь**, который работает с сервисом в этот же момент, я не замечаю задержек из-за чужих тяжёлых ссылок.
- Как **гость** публичного вишлиста, я открываю страницы без задержек, даже когда владельцы добавляют товары.
- Как **администратор/разработчик**, я хочу, чтобы разбор тяжёлых страниц не приводил к зависанию сервиса и не требовал ручного вмешательства.

## Definition of Done

1. Разбор HTML страницы размером более 1 МБ не блокирует обработку других запросов: параллельные лёгкие запросы получают ответ без заметной задержки (измеряется автоматическим тестом).
2. Результат извлечения метаданных (название, изображение, цена, валюта, магазин, fallback-поведение) для всех существующих тестовых страниц идентичен прежнему.
3. Оба пути, где происходит разбор страницы (предпросмотр ссылки при добавлении желания и сервис получения метаданных по URL), не блокируют обработку других запросов.
4. Ошибки разбора по-прежнему обрабатываются прежним образом (понятный fallback пользователю, без падения сервиса).
5. Существующие защитные ограничения (лимит размера ответа, защита от SSRF, anti-bot fallback) не ослаблены.
6. Все существующие тесты проходят, добавлены тесты на неблокирующее поведение, статический анализ проходит без ошибок.
7. Решение задокументировано для разработчиков.

## Task Description

**Проблема.** Извлечение метаданных из HTML (`HtmlMetadataExtractor.extract`) выполняется синхронно и занимает процессорное время. При большом документе (>1 МБ) оно блокирует общий цикл обработки запросов сервиса.

**Область (in scope):**
- Все места, где вызывается извлечение метаданных из загруженного HTML (предпросмотр ссылки, сервис получения метаданных по URL).
- Тесты, подтверждающие неблокирующее поведение и неизменность результата.
- Обновление документации для разработчиков.

**Вне области (out of scope):**
- Изменение логики извлечения (JSON-LD, OpenGraph, правила маркетплейсов).
- Изменение лимитов размера ответа, сетевой загрузки и SSRF-защиты.
- Изменение пользовательского интерфейса и формата ответов.

**Основные сущности (бизнес-уровень):**
- *Страница товара* — HTML-документ магазина, потенциально тяжёлый.
- *Метаданные товара* — название, изображение, цена, валюта, магазин.
- *Предпросмотр ссылки* — результат, показываемый пользователю при добавлении желания (в т.ч. fallback при ошибке).
- *Прочие пользователи сервиса* — чья отзывчивость не должна страдать.

**Нефункциональные требования:**
- Производительность: задержка ответа на лёгкие запросы во время разбора тяжёлой страницы не должна заметно расти.
- Надёжность: ошибки и таймауты разбора не роняют сервис.
- Совместимость: публичные контракты и формат результата не меняются; нет регрессии точности извлечения.
- Сопровождаемость: язык реализации — Python 3.12+, в рамках стека проекта (см. `doc/dev/architecture.md`).

**Ограничения и допущения:**
- Решение должно работать в текущем окружении развёртывания без ручной настройки.
- Новые внешние зависимости допустимы только при явном обосновании на Шаге 2; поведение не должно зависеть от них непредсказуемо.
- Порог «тяжёлой» страницы — около 1 МБ (по описанию задачи); максимальный размер ответа ограничен существующим лимитом загрузки.

## Q&A

- **Q:** Зачем нужна задача с точки зрения бизнеса?
  **A:** Чтобы тяжёлые страницы магазинов не замораживали сервис для всех пользователей; см. «Goals».
- **Q:** Какой вариант решения выбрать: отдельный поток или быстрый C-парсер?
  **A:** Это архитектурное решение, фиксируется на Шаге 2. Требование: не блокировать обработку других запросов, не меняя результат.
- **Q:** Должен ли результат извлечения измениться?
  **A:** Нет, поведение и формат результата сохраняются.
- **Q:** Какой язык реализации?
  **A:** Python 3.12+ (существующая кодовая база `wishenka/`).
