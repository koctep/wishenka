# WISHENKA-145: Добавить smoke-тест с настоящим htmx вместо заглушки

Тип: Debt, 3 SP, приоритет Low. Источник: `ai-tasks/WISHENKA-110/60-tech-debt.md` (follow-up 3).

## Goals

Существующие браузерные тесты списка желаний (`WISHENKA-110`) используют упрощённую заглушку вместо настоящего `htmx` и авторизацию через заголовок `Bearer` вместо пользовательской cookie-сессии и CSRF-защиты. Из-за этого автоматические проверки не ловят:

- поломки декларативной разметки `hx-*` в шаблонах (например, кнопки перемещения элемента);
- регрессии при обновлении версии `htmx` или изменении семантики событий `htmx`;
- ошибки клиентской логики передачи CSRF-токена (`hx-headers` / `htmx:configRequest`) и работы cookie-сессии;
- тихое расхождение между внешними URL скриптов в основном шаблоне и перехватом этих URL в тестовом драйвере.

Бизнес-цель: владельцы и соавторы вишлистов, а также команда разработки должны быть уверены, что реальное взаимодействие пользователя с кнопками `htmx`, cookie-сессией и CSRF-защитой работает в браузере без регрессий после правок шаблонов, клиентских скриптов или версии `htmx`, а все проверки выполняются офлайн и детерминированно в CI.

## User Stories

- Как владелец или соавтор (администратор) вишлиста, я хочу, чтобы нажатие кнопки перемещения желания в списке корректно отправляло запрос через `htmx` с моей сессией и CSRF-защитой и обновляло разметку списка, чтобы порядок желаний надёжно менялся.
- Как разработчик, я хочу иметь автоматический браузерный smoke-тест на настоящем `htmx` с реальной cookie-сессией и CSRF-логикой, чтобы изменения разметки `hx-*`, клиентских обработчиков `htmx` или версии `htmx` ловились до релиза.
- Как ответственный за CI, я хочу, чтобы тест работал полностью офлайн (на локальной закреплённой копии `htmx.org@1.9.12` без загрузки из сети при запуске), был быстрым, ограниченным по времени и проверял согласованность URL перехвата с `base.html`.

## Definition of Done

1. В тестовых ресурсах (`tests/browser_assets/`) используется локальная закреплённая копия настоящего `htmx.org@1.9.12` (без сетевых обращений во время прогона тестов).
2. Реализован браузерный smoke-тест с настоящим `htmx`, который:
   - открывает страницу списка желаний с аутентификацией через cookie-сессию (без подстановки `Bearer`-токена);
   - нажимает реальную кнопку перемещения желания с `hx-post` (вверх или вниз);
   - проходит реальный цикл CSRF-защиты (`hx-headers` / `htmx:configRequest`);
   - проверяет фактическое обновление списка в DOM после ответа сервера и сохранение порядка элементов.
3. Smoke-тест завершается без ошибок и предупреждений в консоли браузера и укладывается в явный таймаут и правила маркировки браузерных тестов.
4. Существующие браузерные тесты на заглушке `htmx_stub.js` продолжают проходить без регрессий.
5. Добавлена автоматическая проверка (guard), подтверждающая, что три внешних URL в `tests/browser_cdp.py` совпадают с URL в `wishenka/web/templates/base.html`.
6. Полный набор проверок проекта (`make check` или релевантный набор тестов с браузерными тестами) проходит успешно.

## Task Description

- **Язык реализации**: Python (автотесты на `pytest` и существующий CDP-драйвер `tests/browser_cdp.py`).
- **Проблема**: заглушка `htmx_stub.js` эмулирует только прямой вызов `htmx.ajax(...)` и `innerHTML`-подмену, не обрабатывает атрибуты `hx-*` и событие `htmx:configRequest`, а тестовая среда подставляет `Bearer`-заголовок вместо cookie-сессии. Кроме того, три внешних URL из `base.html` продублированы в `tests/browser_cdp.py` без автоматической сверки.
- **Границы (Scope)**:
  - один небольшой браузерный smoke-тест с настоящим `htmx.org@1.9.12`, реальной кнопкой перемещения на `hx-post`, cookie-сессией и CSRF-логикой (`hx-headers` / `htmx:configRequest`);
  - использование локального вендорного файла `htmx` без загрузки из интернета во время запуска тестов;
  - проверка совпадения трёх внешних URL в `tests/browser_cdp.py` и `wishenka/web/templates/base.html`.
- **Не входит в задачу (Non-Goals)**:
  - перевод всех существующих браузерных тестов с `htmx_stub.js` на настоящий `htmx`;
  - изменение продуктовой логики перемещения, CSRF или аутентификации;
  - тестирование всех `hx-*` сценариев приложения (бронирования, модальных окон редактирования и др.) — только минимальный smoke-тест для закрытия пробела достоверности;
  - рефакторинг или объединение старых CDP-клиентов (`WISHENKA-146`) и настройка загрузки артефактов CI (`WISHENKA-147`).
- **Ограничения и допущения**:
  - отсутствие сетевых запросов наружу во время прогона тестов (критерий офлайновости из `WISHENKA-110`);
  - вендорная копия `htmx` (`htmx-1.9.12.min.js`) уже присутствует в `tests/browser_assets/`, а её актуальность и лицензионный файл должны учитываться при подключении в тесте.

## Q&A

- **Зачем нужен отдельный smoke-тест на настоящем `htmx`, если 53 теста `WISHENKA-110` уже зелёные?**
  Существующие тесты проверяют поведение собственного JS на заглушке `htmx_stub.js` и с `Bearer`-авторизацией. Они не проверяют реальную обработку `hx-post`, обновление разметки силами `htmx`, работу `htmx:configRequest`/`hx-headers` для CSRF и cookie-сессию.
- **Почему `htmx` должен браться из локального файла, а не по сети?**
  Браузерные тесты обязаны быть детерминированными и проходить в офлайн-окружении без зависимости от внешнего CDN.
- **Нужно ли переписывать остальные тесты на настоящий `htmx`?**
  Нет, в рамках этой задачи требуется только один небольшой smoke-тест и проверка совпадения трёх URL между `tests/browser_cdp.py` и `wishenka/web/templates/base.html`.
