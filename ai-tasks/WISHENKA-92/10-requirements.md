# WISHENKA-92: Исключение окна DNS Rebinding (TOCTOU) при исходящих запросах предпросмотра ссылок

## Goals

Сервис **«Вишенка» (Telegram Wishlist Service)** загружает публичные веб-страницы по ссылкам пользователей для автоматического предпросмотра товаров. В рамках базовой защиты от SSRF (WISHENKA-54) сервис уже проверяет целевые IP-адреса перед отправкой запроса. Однако при раздельном выполнении проверки доменного имени и фактического сетевого подключения сохраняется временной зазор (Time-of-Check to Time-of-Use, TOCTOU), который позволяет обойти защиту с помощью атаки **DNS Rebinding**.

Бизнес-цель задачи **WISHENKA-92** — полностью устранить уязвимость DNS Rebinding (TOCTOU) при загрузке внешних ссылок:

1. **Гарантия целостности проверки безопасности (Zero TOCTOU Window)**:
   - Сетевое соединение должно устанавливаться строго с тем проверенным IP-адресом, который прошёл политику сетевой безопасности, без повторного обращения к DNS на этапе открытия соединения.
   - Злоумышленник, управляющий внешним DNS-сервером с нулевым или минимальным временем жизни записей (TTL), не должен иметь возможности подменить публичный IP-адрес на внутренний (loopback, приватную подсеть или адрес облачных метаданных) между моментом проверки и моментом подключения.

2. **Сохранение корректной работы с легитимными интернет-магазинами**:
   - Использование проверенного IP-адреса для подключения не должно нарушать работу сайтов на общем хостинге, за CDN или с защищённым HTTPS-соединением.
   - Целевой веб-сервер и проверка подлинности защищённого соединения должны по-прежнему ориентироваться на исходное доменное имя из ссылки пользователя.

3. **Надёжность и предсказуемый пользовательский опыт**:
   - При блокировке небезопасного адреса или ошибке подтверждения подлинности сервера сервис должен безопасно переходить в режим ручного заполнения карточки желания, не раскрывая внутренних деталей ошибки пользователю.

## User Stories

### Роль 1: Специалист по информационной безопасности / Администратор платформы

- **US-1**: Как администратор платформы, я хочу, чтобы исходящее сетевое соединение устанавливалось исключительно с тем IP-адресом, который прошёл предварительную проверку безопасности, чтобы исключить обход SSRF-защиты через DNS Rebinding.
- **US-2**: Как администратор платформы, я хочу, чтобы на каждом шаге цепочки HTTP-перенаправлений (redirects) адрес назначения проверялся и фиксировался для подключения единовременно, без повторного независимого разрешения доменного имени.
- **US-3**: Как администратор платформы, я хочу, чтобы при подключении по зафиксированному IP-адресу сохранялась строгая проверка подлинности HTTPS-сертификата для исходного доменного имени, чтобы исключить риск подмены сервера (MITM) или ослабления TLS-безопасности.

### Роль 2: Пользователь вишлиста (Владелец / Соавтор)

- **US-4**: Как пользователь, добавляющий ссылку на товар из интернет-магазина (включая сайты за CDN или на виртуальном хостинге), я хочу, чтобы предпросмотр товара продолжал работать корректно и без ложных отказов.
- **US-5**: Как пользователь, указавший недопустимую или скомпрометированную ссылку, я хочу, чтобы сервис безопасно переходил в режим ручного ввода данных без зависаний и технических сбоев.

Задача WISHENKA-92 считается выполненной в части требований при соответствии следующим критериям приёмки:

1. **Единое разрешение и фиксация IP-адреса (Pinned IP)**:
   - [x] Зафиксировано требование: для каждого исходящего запроса (и каждого шага перенаправления) доменное имя разрешается и валидируется до установления соединения, а само соединение устанавливается напрямую с проверенным IP-адресом без повторного DNS-запроса.
   - [x] Исключена возможность подключения к запрещённому IP-адресу в сценарии, когда внешний DNS-сервер возвращает публичный IP при первом запросе и приватный/служебный IP при последующем.

3. **Поддержка цепочек перенаправлений и Graceful Fallback**:

   - [x] При блокировке, отказе соединения или несоответствии сертификата исходному домену запрос безопасно прерывается с переходом в штатный режим ручного ввода.

## Task Description

### Постановка проблемы

При предпросмотре ссылки сервис сначала определяет IP-адреса домена и проверяет их по политике сетевой безопасности (блокировка loopback, RFC 1918, link-local, адресов облачных метаданных и т. д.). Если после этой проверки сетевой слой выполняет собственное независимое разрешение доменного имени при открытии соединения, возникает окно уязвимости TOCTOU:

- Первый DNS-ответ (на этапе проверки) возвращает легитимный публичный IP-адрес.
- Второй DNS-ответ (в момент установления соединения) возвращает внутренний адрес (например, `127.0.0.1` или `169.254.169.254`), что приводит к выполнению запроса во внутреннюю инфраструктуру в обход проверки.

### Функциональные границы (Scope)

- **Входит в объём задачи**:
  - Устранение повторного DNS-разрешения между валидацией адреса и установлением сетевого соединения.
  - Передача исходного доменного имени целевому серверу и механизму проверки подлинности защищённого соединения (HTTPS) при подключении напрямую к проверенному IP-адресу.
  - Единообразная работа для прямых запросов и всех шагов HTTP-перенаправлений.
  - Сохранение штатного механизма мягкой деградации (Graceful Fallback) при любых ошибках валидации или проверки сертификата.

- **Не входит в объём задачи**:
  - Изменение перечня запрещённых IP-диапазонов или лимита размера ответа (2 МБ), определённых в WISHENKA-54.
  - Вынос настроек SSRF-политики в конфигурацию приложения (отдельная задача WISHENKA-93).
  - Кэширование DNS-ответов в памяти (отдельная задача WISHENKA-94).
  - Расширение тестового покрытия редких форматов IPv6 и длинных цепочек редиректов вне контекста фиксации IP (отдельная задача WISHENKA-95).
  - Изменение логики извлечения метаданных из HTML-страниц.

### Нефункциональные требования

- **Язык разработки**: Python 3.12+.
- **Безопасность**:
  - Нулевое окно TOCTOU между проверкой IP-адреса и установлением TCP/TLS-соединения.
  - Запрещено отключение или ослабление проверки TLS-сертификатов при подключении по IP-адресу.
- **Совместимость и производительность**:
  - Отсутствие деградации совместимости с публичными HTTP/HTTPS-ресурсами (включая виртуальный хостинг и CDN).
  - Отсутствие заметного увеличения задержки предпросмотра ссылок в рамках существующего бюджета времени операции.

### Концептуальные сущности предметной области

1. **Проверенный сетевой адрес (Validated Endpoint IP)**: Конкретный публичный IP-адрес, полученный в результате разрешения доменного имени и подтверждённый политикой сетевой безопасности.
2. **Привязка соединения к адресу (IP Pinning)**: Инвариант, гарантирующий установление сетевого соединения строго с проверенным сетевым адресом без повторного обращения к DNS.
3. **Идентификатор целевого домена (Original Host Identity)**: Исходное доменное имя из URL, используемое для корректной маршрутизации на веб-сервере и подтверждения подлинности HTTPS-сертификата.
4. **Безопасное состояние деградации (Safe Fallback State)**: Штатный режим сохранения желания с ручным заполнением полей при блокировке небезопасного запроса или сбое проверки подлинности ресурса.

## Q&A

- **Вопрос**: Почему нельзя просто запретить домены с низким TTL?
  - **Ответ**: Контроль TTL на стороне клиента ненадёжен, так как атакующий может возвращать произвольный TTL или менять запись независимо от заявленного TTL, а локальный резолвер ОС или кэш могут вести себя по-разному. Единственная надёжная гарантия — использовать для подключения ровно тот IP-адрес, который уже прошёл проверку.
- **Вопрос**: Зачем сохранять исходное доменное имя при подключении по IP?
  - **Ответ**: Большинство современных сайтов размещаются на общем хостинге или за CDN, где один IP-адрес обслуживает множество доменов, а HTTPS-сертификаты выдаются на доменное имя, а не на IP-адрес. Без передачи исходного домена легитимные ссылки будут отклоняться сервером или не пройдут проверку сертификата.
